# 03b / 03c · 动作迁移与白膜参考 · 第二轮调研（2026-10-22）

> **一句话**：两条线（单人用深度视频，多人和动作戏用 Blender 白膜）本质上都是给视频模型提供「几何约束」，可以合并成一层**几何约束层**：三种来源（源视频深度、源视频重建、agent 在 Blender 里编排）共用同一批下游生成器。这一轮最大的变化有三条：
> 1. **许可**：MiniMax H3 全家族禁止在美国使用或展示产出，而我们做的是美国区。
> 2. **白膜消费端**：2026-09-22 出了官方的「灰模视频 → 成片」开源模型（LTX-2.5 Layout-to-Render）。
> 3. **白膜生产端**：2026-08-23 起 ComfyUI 原生支持 SAM 3D Body，可以从源视频直接渲出多人人偶视频，而且许可可商用。
>
> 以上全部没有经过我方 GPU 实测。第 8 节的 P0 实验要先做。

- **调研方法**：分 4 路调研（A 单人深度线、B 源视频转白膜、C agent 接 Blender、D 生成端与多人身份绑定），每路配 1 个反驳式核实代理。用 gh api、Hugging Face API、LICENSE 原文和 ComfyUI 源码核对。候选共 96 个；核实了 67 条关键说法，其中 38 条成立、28 条部分成立、1 条无法核实、0 条不成立，没有发现编造的项目。部分成立的条目主要错在许可细节和措辞过强。
- **原始数据**（每个候选的许可、活跃度、出处，以及每条核实结论）：[动作迁移与白膜调研-2026-10-22.json](动作迁移与白膜调研-2026-10-22.json)
- **第一轮调研**：[视频反推白膜调研.json](视频反推白膜调研.json)（10-12）、`stages/03-produce/greybox-director/README.md`、`stages/03-produce/motion-transfer/README.md`，以及 Obsidian「04 灰模预演管线」「06 云端ComfyUI」。
- **证据等级**：【实测】【源码】【文档】【第三方】【推断】【未知】。本轮只有 C 路在 Mac 上实测了 Blender 无头运行和 GLB 导出，其余全部是文档或源码级。

## 3. 单人线：深度视频动作迁移

**结论**：「深度承载一切」站不住。合理的分工是：**深度负责机位和场景，姿态负责四肢，首帧和提示词负责外观与道具**。在许可安全的候选里，还没有一个经过我方实测。

| 角色 | 首选 | 备选 | 状态 |
| --- | --- | --- | --- |
| 控制视频 | VDA-Small 或 DA3-Mono（深度，缩到 320–640 宽，避免带出原人体型）+ SDPose / DWPose（姿态）；SAM 3.1 抠出主体，只留人物深度 | ReShot（Apache，一条命令出深度、骨架、线稿控制视频，52★，很早期） | 【文档】 |
| 外观与道具 | Qwen-Image-Edit 2511 精修首帧，剑画在首帧里，提示词写明 | — | 已有管线【实测】 |
| 生成（控制类） | Wan2.2 VACE-Fun-A14B（深度 + 姿态 + 参考图） | Wan2.2-Fun-A14B-Control | 都不在 Zealman 镜像里，需下载 |
| 生成（端到端，快速通道） | Wan-Animate-2（Zealman 已有） | SCAIL-2 端到端模式（提示词写全服饰和手持物，开 Relighting LoRA） | 待测 |
| 生成（读原片像素的编辑类，基线） | Bernini-R（现有基线） | Bernini v2、JoyAI-Video-Edit（Apache，16B，08-04） | R 版已【实测】 |
| 能力上限参照（不进生产） | H3 + Fun-Controlnet-Union-2.0（深度 0.3 + 姿态 0.7）、Viggle-Animate | — | 美国许可红线 |

- **评测要量化**：剑可见的帧占比、姿态误差、旧服饰残留面积、机位漂移、耗时、峰值显存。避免又变成主观比较。
- **增加一组预处理对照**：三类模型共同的弱点是醒目服饰残留，可以先把服饰区域灰化或抹平再生成。

## 4. Blender 做法 1：源视频 → 白膜视频 → 目标视频

三种实现，**推荐混合使用，不二选一**：

| | 重建式：SAM 3.1 + SAM 3D Body 渲染 | 程序化：深度 + 法线 + 实例灰阶 | 生成式：视频编辑模型「转成灰色人偶」 |
| --- | --- | --- | --- |
| 动作和运镜 | 中（逐帧估计，快动作和重遮挡会抖动、丢人） | 高（逐帧后处理，不丢动作） | 中到高 |
| 多人 | **中到高**（每人一个网格，彻底避开深度重叠）；SAM-Body4D 专门处理遮挡和 ID 一致 | 中（靠实例掩码上色） | 低到中 |
| 去身份 | **高**（人偶无脸、无服饰；头部要简化） | 中到低（面部起伏、服饰褶皱会残留） | **不可控**（社区里没有现成的灰模或人偶视频 LoRA） |
| 道具 | 没有（可试 SAM 3D Objects 给剑单独建网格） | 有 | 有 |
| 成本和自动化 | 低，ComfyUI 节点链固定 | 最低，但要自己拼节点（NormalCrafter 有官方模板） | 中，需要逐镜验收 |
| 许可 | 可商用 | 按组件选 Apache 档 | 看模型 |

**推荐**：人物用重建式，背景和道具用程序化，生成式只给少数要保留披风或刀的镜头兜底。

**两个细节**：
- `person_palette_falloff` 的作用是往白色去饱和，不是按灰阶区分每个人。要做到「每人不同灰度」，得自己处理。
- 默认着色是不是接近 0.78 灰【未知】。首测时把着色器固定为 normals 或 depth，然后读回像素确认。

**第一块试金石**：方舟 Seedance 2.5 会不会把白膜视频当成真人拦截。官方文档和第三方教程都没提，见 P0-2。

**中期**：用重建式流水线批量生成「真人 ↔ 灰模」配对数据，训练一步式的「真人转灰模」模型。底座选 **Bernini-R（Apache，训练代码已开源）**，不选 LTX，因为 LTX 的商用训练要付费，派生模型还得沿用同一协议。

## 5. Blender 做法 2：agent 接 Blender，编排后导出 GLB 和白模视频

**结论**：这条路已经能做。真正的缺口是**多人接触动作的编排**，不是 Blender 无头运行。

- **桥接**：批处理走「agent 写声明式 shot_spec.json → `blender -b -P`」，确定性最好；交互排错时再用 MCP，选项有官方 Blender Lab MCP、dcc-mcp-blender（MIT，原生支持无头，带骨骼和重定向工具）。官方 MCP 一个连接只处理一次请求，不适合长任务。
- **现成的参照**：**CozyClay**（AGPL，浏览器端开源 previs，3.0 于 10-19 发布）。它的做法几乎就是我们要的：agent 写规格，动作经确定性编译，再做碰撞、滑步、够取、接触的 QA，最后导出首帧、灰模 mp4、相机和提示词，自带 MCP。作者在 v3 里删掉了生成式动作后端。**自研 32–48 人天之前，先用它做一个两人对打镜头。**
- **动作来源**：
  - 武打主料用 Quaternius CC0 连招片段，配合手写的接触对时（两骨 IK 加根偏移，受击帧对齐）；
  - Kimodo 负责走位、转身、非接触动作（单角色，有 2D 根路径和关键帧约束）；
  - 从参考片提取动作走 GEM-X（SOMA 骨架）。
  - 全程尽量**只用一套骨架**，避免 SOMA、Quaternius、Mixamo 三套之间来回重定向。
- **导出**（C 路实测）：GLB 里有相机和骨骼动画，但每个对象各出一个动画片段，Track-To 约束会被烘焙，**镜头焦距动画不会导出**，所以要另存 `cam_info.json`（逐帧 K、w2c、lens）。Seedance 只吃 mp4，GLB 只用于存档、three.js 预览和下游相机条件。
- **踩坑记录**：直接给骨骼的 location 打关键帧，用的是骨骼局部坐标轴，人偶会「飞起来」。根运动要加在对象或专门的根骨骼上，按世界坐标换算。
- **环境风险**：ROG 通过 SSH 访问，Windows 的 SSH 会话没有交互桌面，WORKBENCH 或 EEVEE 在 `-b` 下仍要建 GPU 上下文，可能失败。WSL2 里没有 `/dev/dri` 时 EGL 会崩，要用 Xvfb。这几种情况都要实测（P0-4）。

## 6. 生成端与多人身份绑定

**按镜头类型选型**（全部待实验）：

| 镜头 | 首选 | 备选 |
| --- | --- | --- |
| 单人、静机位、要 1:1 | Wan-Animate-2 或 SCAIL-2 端到端（驱动用源视频或白膜） | Bernini-R、VACE-Fun（深度 + 姿态） |
| 单人、大运镜 | LTX-2.5 Layout-to-Render + 首帧锚定 | Seedance 2.5 白模参考 |
| 双人、静机位 | SCAIL-2 吃网格渲染加 Blender 逐人颜色遮罩（参考拼贴按从左到右排） | Layout-to-Render |
| 双人交叉、群戏（≤6 个有名角色） | Layout-to-Render + 首帧、中间帧、尾帧锚定 | 分组再做 SCAIL-2 替换 |
| 群戏，超过 6 人 | 有名角色同上；路人在首帧里统一画成群演 | 没有方案能绑定 7 个以上具名角色 |
| 允许重编排 | Seedance 2.5（白膜同时是去身份层） | Kling 3.0 Omni、Higgsfield Genjutsu |

**多人身份绑定**：没有任何模型能直接实现「第 N 个人偶 = 第 N 个角色」。目前最稳的是**在图像域绑定**：
1. 把灰模首帧里每个人偶涂成醒目的颜色；
2. 用 Qwen-Image-Edit 2511 按「红色人偶 = 图 1，蓝色人偶 = 图 2」做多图编辑；
3. 用边缘 PSNR（约 17 以上）和 50% 叠加图做质检；
4. 交给 Layout-to-Render 或 SCAIL-2 传播到整段。

因此多人能不能成，**先看多人首帧编辑的成功率**（P1-4）。fal 的同类流程用的是闭源 Nano Banana Pro，而且画面里没有人物，不能当作多人证据。

**硬件**：LTX-2.5 nvfp4（18.7GB）加 int8 Gemma 编码器（15.4GB），合计约 34GB，超过 5090 的 32GB，要在编码后卸载编码器。4090D 基本不适合跑 LTX-2.5，适合跑 SCAIL-2、Wan-Animate-2、Bernini 和图像编辑。

## 7. 统一架构：几何约束层

用户的判断「深度迁移和 Blender 本质相同」得到支持。建议把 03b 和 03c 合并成一层，按「来源 → 约束产物 → 消费端」组织：

```
来源                                   约束产物（统一规格）                     消费端（Hypit Provider）
① 源视频 → 深度/姿态（单人）       ┐   control.mp4（深度/姿态/白膜，24fps）   ┌ Seedance 2.5 reference / edit
② 源视频 → SAM 3D Body 重建（多人）├→  id_mask.mp4（逐人纯色，≤6 色）       ─┼ LTX-2.5 Layout-to-Render
③ agent → Blender 编排（原创/动作戏）┘  first_frame.png（身份锚定后）         ├ SCAIL-2（网格驱动 + 遮罩）
                                         cam_info.json（K, w2c, lens）          ├ Wan-Animate-2 / VACE-Fun
                                         shot_spec.json（谁在哪、做什么）        └ Bernini-R（编辑基线）
```

- 三种来源的产出规格一致，消费端不用关心约束是从哪来的；
- 单人镜头也值得跑一次 Layout-to-Render 和 SCAIL-2 网格驱动，和深度线对比。如果一条链路就能覆盖所有镜头，就不必维护两套工作流（D 路核实代理的建议）；
- 每个消费端包装成 Hypit Provider，复用 plan、报价、钉住结果的流程（03b README 的既定方向）。

## 10. 主要未知

- 方舟对灰模和人偶视频的真人检测是否放行，脸部起伏到什么程度会被拦。
- Layout-to-Render 在多人、快动作、交叉遮挡下的表现：模型卡没有多人评测，也没有第三方测试。
- SCAIL-2 和 Wan-Animate-2 能不能把灰色人偶当驱动视频：两者都是用真人动作训练的。
- Wan-Animate-2 的「多对多驱动」怎么输入：README 没写。
- SAM 3D Body 在快动作、重遮挡下的抖动和 ID 切换率。
- LTX-2.5 在 5090 上的实际峰值显存和耗时。
- 在 ROG 上，通过 SSH 启动的 Blender 能不能无头渲染。
- Kimodo 的武打动作质量：只有官方文字说训练数据含游戏战斗，没有评测。
- 价格：Seedance、Kling、Runway 的价格多来自转售商，彼此冲突，只能当量级参考；Kling 4.0 是否已发布，各来源说法冲突，不进预算。
